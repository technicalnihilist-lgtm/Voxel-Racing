# Changelog

**Daily maintenance campaign — 1 to 20 November 2026, 10 updates per day.**
The UI is frozen: no entry below changes CSS, HUD, menus, layout or styling.
Every item is a bug fix, a performance optimisation or a fluidity improvement.

## 2026-10-31 — pre-campaign fixes
- Fixed a per-frame exception (`rp` was both the rain-drop array and the roll-rate spring) that aborted the render loop every frame.
- Cockpit camera sat *inside* the car body; it is now a hood cam just above the roof.
- Added lateral tyre grip + a grip-based yaw cap: the car tracks its nose instead of spinning out off-road (slip angle 23° → 7°).
- Replaced the teleporting off-road clamp with real guardrails; the rail now guides the car along instead of stopping it dead.
- Clamped suspension travel so a hard impact can no longer tilt the body through the floor.
- Wet asphalt re-tuned: dark and glossy instead of washed-out white.
- Countdown now runs on wall-clock time, so it no longer drags on slow devices.
- Default quality raised to High; adaptive resolution floored at 85% so the image never goes blurry.

## 2026-11-01
- Ground plane snapped on an 8-unit grid while its grass texture tiles every 10 units, so the grass pattern jumped 0.8 of a tile every 8 m of travel — a visible shimmer/pop under the car. The ground now snaps on whole 10-unit tiles, which makes each jump an exact tile and the pattern world-locked (no pop).
- Tree collision boxes sat 3 m inside the trees they belonged to: the scenery places a tree at `14 + rand*25` units from the centre line, but the collision test used `11 + rand*25`, so every tree was an invisible obstacle a few metres nearer the road and could be driven straight through at its real position. The collision query now uses the same offset as the renderer, so you hit exactly the trunk you can see.

The outgoing model now releases the geometries and materials it owns, skipping the handful shared with the traffic cars; the same 12 switches now stay flat (132 to 135).
## 2026-11-02
- Restarting from the main menu started the race on empty grass: `newGame()` puts the car back at z=0 but only cleared the segment cursor (`curK=-1e9`), and the scenery is rebuilt inside the `play` branch of the loop, so the whole three-second countdown played over the bare ground plane and the road, rails and trees popped in at GO. `newGame()` now rebuilds the scenery for the new position immediately, so the countdown starts on a complete track.
- Restarting a race rewound the skid-mark ring buffer (`skidI=0`) but never cleared the instance matrices, so every tyre mark laid in the previous race stayed on the road for the rest of the session — black streaks where you had not driven this time, and only the first few of them ever got overwritten. `newGame()` now resets all 260 skid instances to the zero matrix, so a restart starts on a clean road.
- Every wheel was built from five separate spoke meshes, so each car spent 20 draw calls on spokes alone and the eight cars on screen at High pushed 562 draw calls a frame. The five spokes are now merged into one geometry per wheel (same boxes, same angles, same triangle count), taking each car from 66 to 50 meshes and the High preset from 562 to 434 draw calls a frame - 128 fewer draw submissions every frame, with the geometry count and the image unchanged.
- Restarting a race left the car and the dash carrying over the previous race: the countdown never calls `step()`, so the speedometer and gear readout still showed the speed you crashed at, and the body-roll/pitch springs plus the steering angle still had the car sitting tilted on the line with its front wheels turned until GO. `newGame()` now zeroes that derived state (forward speed, slip, throttle, brake, steer angle, body sway and load transfer), so a restart begins from a settled car.
- The particle system walked all 600 slots, re-uploaded four attribute buffers (~19 KB) and drew the mesh every single frame, even when no particle was alive - and spray only exists in the wet, dust only off-road and sparks only on a hit, so most frames have none at all. It now tracks how many particles are live and, with none, skips the loop, the uploads and the draw call; on the frame the last one dies it still uploads the zeros and hides the mesh, so the picture is unchanged.
- Leaving the game in a background tab left the engine droning: a hidden tab stops the render loop, so `audio()` never ran again and the engine, tyre and rain gains stayed frozen at whatever they held when you switched away, even though the race had already been paused. The visibility handler now mutes those three gains as well, and the first visible frame restores them from the physics state - same engine sound while you drive, no noise from a tab you are not looking at.

## 2026-11-03
- The race clock was running during the standing start: `tt` accumulated on `state==='play'||state==='count'`, so the HUD read 0:03.0 the instant the lights went out and every checkpoint message was inflated by the three-second wait, even though `step()` never runs and the car cannot move before GO. The clock now only accumulates in `play`, so the first frame of a race reads 0:00.0 and checkpoint splits are real race time.
- `spawn()` picked a lane and a distance for a traffic car but never wrote its transform - the only code that positioned traffic lived in the `play` branch of the loop, so from the first frame until GO all seven cars sat stacked on one point at the world origin (the road passes through that spot at z=1354) and then teleported onto the track the instant the lights went out. `spawn()` now places the mesh as well, so cars are already sitting on the road through the menu and the countdown and nothing pops in at GO.
- The Ultra preset's render scale was the device pixel ratio itself (`pr:Math.min(devicePixelRatio,2)`), while `resizeView()` already multiplies every preset by `min(devicePixelRatio,1.75)` - so the ratio was counted twice, and only on Ultra. On a 1x display Ultra rendered at exactly the same resolution as High (a no-op preset), and on a 2x display it jumped to 3.5x, i.e. 6.17 MP against High's 1.54 MP - four times the fill cost for one step up in the menu, enough to stall a phone. Ultra is now `pr:1.25`, a plain multiplier like Low/Med/High: 0.79 MP against High's 0.50 MP on a 1x screen, and 2.41 MP against 1.54 MP on a 2x screen. Same look, one preset step above High, and no longer a framerate cliff.
- Traffic cars' wheels turned at `v/.38` while the player's do `v/.6` - the same .41-radius wheel, scaled 1.5, so the same physical wheel rolling on the same road. Every traffic car's wheels therefore spun 58% faster than the car was moving (20 m/s looked like 8.4 rev/s instead of 5.2, near enough to the five-spoke spacing to judder and read as wheelspin when you pass one). The traffic loop now uses the same `/.6` divisor, so a traffic wheel turns exactly as far as its car travels; no geometry, material, speed or handling value changed.
- `rebuild()` lays out the road, rails, trees, buildings and rocks for all 150 segments every time the car crosses a 4 m boundary — 12 to 20 times a second at race speed — and each of those ~2,500 instance transforms was built by setting an `Object3D`'s position/rotation/scale, letting it convert the Euler to a quaternion and run `Matrix4.compose`, then copying the 16 floats out. Nothing in the scene is ever rotated about anything but Y, so `put()` now composes that matrix straight into the instance buffer. The matrices are bit-identical (checked element-for-element across six track positions and all four quality presets, and the rendered frames match), and `rebuild()` falls from ~0.70 ms to ~0.46 ms at High — a third off the heaviest thing the main thread does during a race.
- The scenery rocks were laid `8+h*10` metres from the centre line, so 45% of them landed on the paved shoulder *inside* the 11.4 m guardrail — well within reach of a car the rail clamps to 9.9 m — and unlike the trees, rocks have no collision test anywhere in the game, so a boulder sitting on the tarmac verge could be driven straight through. They now start at the 14 m the trees use, which puts the nearest rock edge at 13.5 m: clear of the car's 11.5 m reach and behind the rail. Verified against the live instance buffer over 49 rebuild windows and 1,039 placed rocks — none inside the rail (was 45%, nearest edge 7.58 m) — with the same rock count, sizes, colours, spread and placement rule as before, and no change to collision, handling or the road itself.
- Every traffic car built two volumetric headlight-cone meshes in `addBeams()`, but the only thing that ever raises their opacity is `updateSky()` writing `car.beamMat.uniforms.uOp` — the player's car. A traffic car's cones therefore sat at alpha 0 for the entire session and were still submitted every frame: with the seven traffic cars of the High preset that was 14 additive, `depthWrite:false` draw calls on every single frame, 14 of the frame's 358 draw calls, for geometry that provably cannot put a pixel on screen. Only the player's car builds them now (its beams still come on at night, uOp 0.5). Verified pixel-identical — zero differing pixels between the frame with the traffic cones and the frame without them, night and day — and a High scene with seven traffic cars falls from 358 to 344 draw calls and from 171,594 to 171,146 triangles.
## 2026-11-04
- A window that loses focus never receives the matching `keyup` - it goes to whichever window took focus - and nothing cleared the held controls, so a key pressed before an alt-tab stayed down for good: the throttle you were holding when you switched away was still held when you came back, and the car had driven on by itself in the meantime. The `visibilitychange` handler only covers a hidden tab, and an alt-tabbed window is not hidden, so the game never saw it. A `blur` listener now releases every control (left, right, throttle, brake, reverse), the same reset `pause()` already does; the car coasts from whatever speed it had instead of accelerating unattended. Measured with the throttle held at 56.7 km/h: before, 2 s of background time took it to 102.9 km/h with `I.g` still 1; now `I.g` is 0 on blur and the car decelerates to 48.8 km/h. No change to handling, controls, physics or the UI.
- Traffic cars had no car-to-car collision at all: a faster car drove straight through a slower one sharing its lane, and a respawn could drop a car inside another, so two cars were visibly intersecting on up to 11% of play frames (411, 157 and 82 of three 60-second runs). A car now eases off as it closes on the nearest car ahead in its own lane and settles one car length behind it - it only ever slows, never moves backwards or teleports - and `spawn()` re-rolls its spot up to six times so it never materialises on top of another car. Three more 60-second runs measured 0 overlapping frames, with the same car count, speed range, spawn band, draw calls and triangles, and no change to handling, controls, the art or the UI.
- A traffic car that eases off behind a slower car in its lane still rolled its wheels at its *nominal* speed rather than the speed it was actually covering ground at, so while it was held up the spokes spun up to 2.46x the ground speed - a car crawling at 36 km/h blurred its wheels as if it were doing 86, and over an 8-second hold-up it turned its wheels 50.9 revolutions for 25.2 revolutions of travel. The wheel update now uses the same eased speed the car is moved by (`tv`), so wheel rotation equals distance/0.6 exactly (simulated worst-case ratio 2.46x -> 1.00x, and 0 error on every visible traffic car in a live headless run), with no change to traffic speeds, spacing, spawning, handling, controls or the UI.
- The rain and snow vertex buffers are sized for the heaviest preset (1,700 drops, 40.8 KB of positions), but only the drops actually in play are drawn — and `needsUpdate` re-uploaded the entire array to the GPU every frame regardless. On the Low preset in rain, 33 KB of that 40.8 KB was spent on drops sitting outside the draw range: five times the data that could reach the screen. Both buffers now upload just the live prefix (`updateRange`), the same floats in the same order. Measured on identical deterministic frames: uploaded vertex data falls from 38,898 to 7,848 bytes a frame in rain (−80%), with the rendered image bit-identical (three frames hashed exactly equal), the same physics state, draw calls (116) and triangles (77,788).
- `rebuild()` rewrites the whole scenery every 4 m of travel, and `upd()` marked each of the 15 instanced meshes for re-upload without saying how much — so every rebuild pushed the *entire* instance buffer to the GPU, including the slots past `count` that the mesh never draws. The buffers are sized for the heaviest preset (400 slots), so at High that was 268 KB of `bufferSubData` per rebuild, and at Low the same 268 KB went up to draw just 140 instances. Each attribute now uploads only its drawn prefix (the same floats, in the same order): on identical deterministic frames, uploaded instance data per rebuild falls from 274,080 to 203,520 bytes at High (−26%) and to 94,940 bytes at Low (−65%), with bit-identical rendered frames (three configs hashed exactly equal), the same draw calls and triangles, and no change to the scenery, collision, handling or the UI.
- The particle system pushed all four of its attributes to the GPU on every frame that had even one particle alive — 19,200 bytes of `bufferSubData` for a spray plume of a few dozen points out of the 600 slots — and the colour buffer was re-uploaded every frame although a particle's colour is written once, in `emit()`, and never changes. `stepParticles()` now uploads only the live slot window and the point mesh draws only that window, and the colour buffer goes up only when `emit()` has written to it. Measured on identical deterministic frames in rain with 31 particles alive: particle vertex uploads fall from 19,200 to ~900 bytes a frame (−95%) and total per-frame buffer traffic from 32,281 to 13,911 bytes (−57%), with three rendered frames hashed exactly equal to the old build (same particles, same positions, same picture) and no change to emission, lifetimes, colours, physics or the UI.

## 2026-11-05
- Every car body was a couple of dozen one-box meshes — bumpers, sills, mirrors, lamps, wing, plate — and every box was its own draw submission, so the eight cars on screen (the player's plus seven traffic cars) cost 372 of the frame's 395 draw calls. The boxes never move relative to the body and share only a handful of materials, so each material's boxes are now merged into one mesh per material (the same boxes at the same transforms with the same normals; the rotations are baked into the vertices, and no car material samples UVs, so nothing about the shading changes). The rim and the five spokes, which are one rigid chrome part, likewise became one geometry. The player's car falls from 50 meshes to 28 and each traffic car from 46 to 26; a High scene with seven traffic cars falls from 395 to 234 draw calls a frame (−41%), the shadow pass from 24 to 7, and the live geometry count from 216 to 86, with the triangle count unchanged at 173,836. Verified by rendering the same deterministic frame on both builds: the player's car and the nearest traffic car are pixel-identical, and the only differences in the whole frame are 0.34% of pixels on cars 50 m and further away, where baking the box rotations into the vertices moves a vertex by an ULP and flips a sub-pixel edge (679 of those 786 pixels differ by 1 of 255). Physics, handling, traffic spacing, spawning, controls and the UI are untouched, and a 60-second headless run through rain, night, steering and a garage switch of all four models produced no errors, no NaN and no geometry growth.
- The skid-mark ring buffer holds 260 marks - 16.6 KB of instance matrices - and every event rewrites exactly the two slots it lays down, but `needsUpdate` pushed the whole array to the GPU: 16,640 bytes of `bufferSubData` for 128 bytes of new data, 24 times in a 3-second full-throttle run, 28% of all the buffer traffic those frames produced. Each event now uploads only the two slots just written (the same floats, in the same order), falling back to the full upload on the one event in 260 that straddles the end of the ring; the per-event upload drops from 16,640 to 128 bytes (-99.2%) and the total buffer traffic of that run from 1,416,960 to 1,020,672 bytes (-28%). The instance data is bit-identical (same array hash on both builds) and, checked against a shadow copy of the GPU buffer after every single upload, the GPU holds exactly what the CPU array holds - in the normal case, on the ring-wrap event, and through `newGame()`'s clear, which now asks for a full upload explicitly so a partial range left pending in the same frame cannot leave the previous race's marks on screen. No change to where or when marks are laid, their size, opacity, timing, physics, handling, controls or the UI.
- "Restart" in the pause menu skipped the standing start: `$('rst')` ran `newGame()` — which resets the car and sets `state='count'`, `cdT=0`, `cdStep=-1` — and then immediately called `resume()`, and `resume()` forces `state='play'`. The countdown the restart had just set up was thrown away, so a restart began instantly with no 3-2-1, no GO and the race clock already running, while Play in the main menu gives the full three-second lights. The handler now closes the pause panel the same way the Play button does and leaves the state machine alone. Verified headless on both builds: before, a restart read `state='play'` with `cdT` 0.00 and the banner empty; after, it enters `count`, shows `3`, and reaches `play` at `cdT` 3.35 with the race clock still at 0:00.0 and the car at rest at z=0. No change to the countdown itself, to handling, controls, physics, HUD or markup, and pause/resume still behave exactly as before.
- The standing start could not be paused: `pause()` began with `if(state!=='play')return`, so the pause button and Escape did nothing at all during the 3-2-1 - the HUD and its pause button are already on screen from the moment you press Play - and the `visibilitychange` handler only paused a running race, so a tab hidden during the lights was never paused and, because the countdown runs on wall-clock time (`cdT=(ts-cdStart)/1000`), you came back to a race already started with the clock running. `pause()` now also accepts `count` (recording which state it came from), and `resume()` re-anchors `cdStart` to `performance.now()-cdT*1000` and rewinds `cdStep` so the banner re-shows the number it stopped on: the countdown carries on from where it was instead of expiring the instant you return, and it is not restarted either. Verified headless on both builds: before, clicking the pause button during the countdown left `state='count'` with `cdT` still climbing (0.83 -> 2.05) and the panel never opened; after, it enters `pause` with `cdT` frozen at 0.62 for the 1.2 s the panel was up, and resume returns to `count` at 0.73, shows `3` then `2`, and reaches `play` at `cdT` 3.02 with the race clock at 0:00.0 - the full three seconds of lights, not the 0.95 s that was left. An uninterrupted start still reads 3-3-2-2-1-1-GO, and pausing a running race still goes `play` -> `pause` -> `play`. No change to the countdown's length, to handling, controls, physics, HUD or markup, and no errors on either build.

## 2026-11-06
- The keyboard could not pause the standing start, even though the pause button could. The countdown was made pausable on 2026-11-05 - `pause()` accepts `count`, `resume()` re-anchors `cdStart` so the lights go out after the full three seconds - but the `keydown` handler still re-tested the state itself and only for `play`, so Escape and P during the 3-2-1 fell through to nothing while the on-screen pause button opened the panel. The same handler also tested lowercase `p` only, while `c`/`r`/`n`/`t` all accept both cases, so Shift+P did nothing in any state. It now delegates to `pause()`/`resume()` (which already know which states they accept) and accepts `P` as well; in the menu and garage both still no-op, because `pause()` returns early there. Verified headless on both builds: before, Escape in `count` left `state='count'` and the clock climbing; after, it enters `pause` with `cdT` frozen at 0.90 for the 1.2 s the panel was up, and Escape again returns to `count` at 1.26 showing `2` and reaching `play` at `cdT` 3.18 with the race clock at 0:00.0. Pausing a running race still goes `play` -> `pause` -> `play`, Shift+P now pauses, Escape in the menu still does nothing, and a 30-second throttle run is unchanged (no NaN, no errors). No change to the countdown, handling, physics, controls, HUD or markup.
